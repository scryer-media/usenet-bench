# Adversarial Usenet suite

`go run ./cmd/adversarial` generates hostile NZBs, raw article bodies and archive
or parity bytes, serves them over a private NNTP listener, and evaluates a
client-neutral observation format. It has no dependency on Weaver, any client's
E2E harness, the throughput fixture matrix, Docker, or an external fixture
download. Its generator uses only the Go standard library.

Every catalog entry has an executable recipe. No archives or encoded copies of
archives are stored in Git. Text fixtures are permitted, but this suite also
generates its text inputs. `generate` requires an existing output directory
outside a Git checkout and refuses to overwrite existing bundles. Generated
files use flat, fixed names; attacker-controlled names exist only *inside* the
NZB, article, archive or PAR2 data, never as generator filesystem paths.

## Generate and inspect

Run from this repository with the same Go toolchain for each comparison:

```sh
go run ./cmd/adversarial list
go run ./cmd/adversarial list --family par2
go run ./cmd/adversarial list --case zip-local-name-mismatch

# Choose an existing scratch directory outside any Git checkout.
go run ./cmd/adversarial generate --output /scratch/adversarial
# Alternatively select one case or one family.
go run ./cmd/adversarial generate --case control-rar5 --output /scratch/controls
go run ./cmd/adversarial verify --bundle /scratch/controls/control-rar5
```

A bundle contains `manifest.json`, `input.nzb`, flat `article-NNN.body` files,
and flat `payload-NNN.bin` files. The manifest records the recipe version, Go
toolchain, case ID and human-readable name, expected behavior, limits, article
IDs, SHA-256 of every input,
and expected delivered payload hashes for controls and successful repairs.

Archive bytes are generated directly. ZIP, TAR, gzip and DEFLATE use standard
library writers or raw documented headers. RAR4 and RAR5 controls contain a
stored member; the 7z control uses the Copy coder. PAR2 controls protect one
slice, allowing independent exponent-zero recovery verification without using
the product's parity implementation. Four additional multi-file recovery cases
cover nine input slices, partial tails, damage beyond the first 16 KiB, exactly
sufficient/surplus recovery and insufficient/dependent equations. Their GF(2^16)
algebra is checked by an installed independent `par2` executable.
Each manifest's `contract` states its baseline, target component, mutation,
invariant, prerequisites and coverage limits. Mutations intended to pass the outer
integrity gate recompute the relevant header/packet checksum. Explicit checksum
failures deliberately do not. An archive with internally consistent checksums
is still untrusted input.

`verify` regenerates the case and compares both its manifest and every artifact.
Editing a manifest to bless different bytes or a different expected outcome
fails verification. Regeneration requires the recorded Go toolchain; compressor
output is not promised byte-identical across different Go releases. Version the
recipe when changing generated bytes or expectations. Archive files are capped
at 16 MiB each and bundles at 64 MiB. Expansion bombs are small compressed
streams that produce 64 MiB + 64 KiB when fully decoded; their generation never
materializes the expanded body in memory or on disk.

Path variants cover parent/absolute/drive/UNC/extended paths, mixed separators,
ADS, device names, Windows GLOBALROOT and device-child paths, NUL/newline,
trailing dots/spaces, reserved staging directories, option/response-file syntax,
shell and PowerShell interpretation, HTML, terminal escape sequences, bidi and
Unicode normalization. They use fixed `/scratch` canaries and `.invalid` network
destinations. Command-injection strings name `adversarial-canary`; the repository
provides an inert, generable recorder that an observer can mount read-only inside
the isolated client environment.

These are attack recipes, not claims that a client is vulnerable or immune. In
particular, malformed encryption/coder metadata does not establish coverage of
valid encrypted or compressed RAR/7z members. Cases that need encryption writers,
BZip2/XZ/Zstd/Brotli generators, complex solid/multivolume seeds, TLS/compressed
NNTP, externally coordinated filesystem races, restart scheduling, sanitizer
builds or additional historical vulnerability reproductions remain extensions. Those are not
represented as passing or skipped catalog entries. A catalog entry or contained
diagnostic run is not proof of immunity.

## Serve the exact bytes

```sh
go run ./cmd/adversarial serve \
  --bundle /scratch/adversarial/zip-local-name-mismatch \
  --listen 127.0.0.1:8119 --duration 1m
```

The first JSON record contains the endpoint, case and manifest digest. Configure
the disposable client under test to use that endpoint and submit `input.nzb`.
`serve --case ID` instead generates the same bundle entirely in memory. Each
client/case run needs a fresh responder so first-attempt faults start at the
same point. First-attempt state persists across reconnects within a run.

The responder supports BODY, ARTICLE, HEAD, STAT, GROUP, MODE READER, DATE,
CAPABILITIES, AUTHINFO and QUIT. It performs NNTP dot-stuffing and can fragment
writes at each declared size. TCP may coalesce writes: a server chunk size does
not prove a client's read size. Protocol-level scripts are independent of any
server's POST normalizer. HEAD/STAT expose fixture availability; the declared
fault modifies BODY/ARTICLE, except capability and authentication scenarios.
The responder does not implement TLS, compression negotiation, POST or a real
authentication boundary. Only synthetic benchmark credentials belong here.

Listen addresses must be loopback IPs. Run the responder within the disposable
network namespace used by the client or use an explicitly configured local
forwarder; the command does not expose a listener to the LAN. Responder limits:
64 active connections, 2,048 total connections, 8,192 commands, 512 MiB response
budget, 4 KiB command buffer and a maximum five-minute lifetime (the default).
Socket deadlines follow that lifetime; reserve time for client startup.
Cancellation closes the listener and sockets and joins workers. Statistics retain
bounded response hashes, article attempt numbers, bytes written, request counts
and stop timestamps. A truncated transcript reports dropped events.
Missing-terminator and slow-body cases end at the responder's lifetime; preserve
whether a client stopped first. Server shutdown is not a client security pass.

## Exploratory client supervision

`cmd/adversarial-supervise` is a Linux-only adapter for exercising the generated
catalog through a one-shot client contract. It accepts explicit case IDs or one
exact family, starts a
fresh in-process responder for each case, records bounded client and syscall
logs, inventories the disposable job root and verifies any expected output. It
requires the exact expected client version and a SHA-256 launcher, image or
distribution identity on every invocation; no product version is compiled into
the adapter. `--client-kind weaver` drives the standalone Weaver CLI directly.
`--client-kind sabnzbd` uses `cmd/sabnzbd-case-client`, which starts a fresh SAB
process, submits through its local HTTP API, polls terminal history and writes
the same one-shot terminal report. A review-required result stops the batch
before another hostile case starts.

The adapter deliberately refuses to provide its own outer isolation. Launch it
inside a new bubblewrap user, PID, mount and network namespace with only
loopback networking, read-only `/usr`, read-only `/opt/weaver`,
`/opt/supervise` and optional `/opt/adversarial-canary`, and no writable host
mounts. `/scratch` must be a private tmpfs
with at least 640 MiB free; 2 GiB is recommended so generated bundles, logs and
retained per-case job roots do not compete with Weaver's 512 MiB spool floor.
Also place the whole namespace in a cgroup with bounded memory, swap, tasks and
CPU. Set `OOMPolicy=continue` so a client OOM does not kill the smaller observer
before it emits the result. Stream stdout to private host storage from outside
the namespace rather than mounting an evidence directory writable inside it.

An abbreviated invocation is:

```sh
systemd-run --user --scope \
  -p MemoryMax=1G -p MemorySwapMax=0 -p TasksMax=256 -p CPUQuota=200% \
  -p OOMPolicy=continue \
  bwrap --unshare-all --die-with-parent --new-session --cap-drop ALL \
  --clearenv --setenv PATH /opt:/usr/bin:/bin \
  --ro-bind /usr /usr --symlink usr/bin /bin --symlink usr/lib /lib \
  --symlink usr/lib64 /lib64 \
  --proc /proc --dev /dev --size 2147483648 --tmpfs /scratch \
  --ro-bind /path/to/weaver /opt/weaver \
  --ro-bind /path/to/adversarial-supervise /opt/supervise \
  --ro-bind /path/to/adversarial-canary /opt/adversarial-canary \
  -- /opt/supervise --output /scratch/results \
  --expected-client-version 'weaver 0.11.3' \
  --cases control-yenc,control-multipart-yenc
```

The normal scratch-capacity check can be bypassed only with
`--allow-low-scratch` for an intentional low-disk liveness regression. Do not
mix such a result into ordinary comparison data. Expected nonzero exits for
`reject` and `contain` recipes are recorded as rejection behavior rather than
supervisor failures. `--unsupported-cases` must be an explicit case allowlist
backed by a separately executed valid control that proves the client lacks the
required capability; it never suppresses canary, inventory, escape or other
review failures. `--expected-stall-cases` applies only to `contain` cases and
records bounded provider-induced nonprogress as `contained_stall`. It also does
not suppress any secondary safety failure, and security remains inconclusive.

Before every case the supervisor creates `/scratch/escape.canary` with fixed
content and verifies it remains unchanged, and verifies that
`/scratch/execution.canary` remains absent. The recorder creates only the latter
file, using exclusive creation, if a command-injection string is actually
executed. Either change is a review-required potential finding that stops the
batch.

The SAB adapter deliberately disables final-filename deobfuscation so exact
fixture names remain comparable. It also marks SAB's initial direct-unpack disk
speed test complete; otherwise that startup probe, rather than the case under
test, consumes the per-process file-size budget. These are comparison-harness
settings, not product defaults, and must be recorded with results.

This adapter is diagnostic evidence, not the independent observer contract
below. The client and observer share one namespace, logs can be modified by the
client, cgroup counters include the observer, and per-client memory, cumulative
writes, sanitizer findings, secret access and queue liveness are not fully
measured. Therefore it always reports security as `inconclusive` unless it sees
a potential finding; it cannot produce a security pass.

## Observe and compare

This command provides generators, a responder, output verification and scoring.
It does **not** launch clients or supply a privileged filesystem/process/network
observer. The existing throughput adapters report completion, so their results
cannot stand in for security observations. Connect your disposable client runner
and independent observer to the explicit JSON contract:

```sh
go run ./cmd/adversarial observation-template --case zip-local-name-mismatch
go run ./cmd/adversarial evaluate \
  --bundle /scratch/adversarial/zip-local-name-mismatch \
  --observation /scratch/private-results/observation.json
go run ./cmd/adversarial plan --clients /scratch/client-identities.json \
  --family par2 --repetitions 3 --seed 42
go run ./cmd/adversarial record --plan /scratch/plan.json \
  --run-id attempt-000001 --observation /scratch/private-results/observation.json
go run ./cmd/adversarial compare-plan --plan /scratch/plan.json \
  --results /scratch/private-results/recorded-results.json
```

The template leaves identity, outcome and resources unset and every security
check `unknown`. The observer fills in client/version/platform, rendered-config
SHA-256, exact manifest digest, terminal outcome, all seven resource counters,
and independent evidence references. Measure the whole client process tree,
including external extractors and repairers. Resource counters are wall and CPU
milliseconds, peak memory bytes, cumulative bytes written, created entry count,
peak open descriptors and connection count. Missing/null counters do not decode
as measured zero. Default client envelope is 60 seconds wall, 30 seconds CPU,
512 MiB peak memory, 64 MiB writes, 4,096 entries, 256 descriptors and 64
connections. These are comparison limits; setting OS resource caps remains the
runner's responsibility.

Required checks are `filesystem_containment`, `process_execution`,
`network_egress`, `secret_redaction`, `privilege_preservation`, `queue_liveness`,
`cleanup`, and `memory_safety`. Each contains `status` (`pass`, `fail`, `unknown`)
and `evidence` (an observer artifact reference). Check that canary files outside
the job root are unchanged, no canary command executed, no unauthorized egress
or secret read occurred, metadata privileges were not restored, and a following
valid job still succeeds. Memory-safety evidence requires suitable instrumentation;
absence of a crash by itself is insufficient. `observer_evidence` binds the
planned attempt, observer/client binary hashes, stopped process tree, assigned
output root, instrumentation stage and whole-tree resource scope. Every observed
check requires a distinct embedded JSON artifact, with SHA-256, run/manifest
binding, collector, instrumentation and detector self-test digest. Resource
evidence must equal all reported measurements. Dropped events, missing artifacts,
reused references and unsupported instrumentation remain inconclusive. Hashes
detect accidental modification, not forgery: a dishonest observer can fabricate
an observation. Platform detector backends are still required.

Stop the client and helpers before verifying delivered files. `output_directory`
is the actual final payload directory, with work/repair sidecars kept separately.
Do not filter or rename client outputs to make the oracle pass. Verification
rejects links, special files, extra payloads, missing files and digest mismatches,
and caps enumeration and bytes read.

Security and behavior are separate columns. Security is `pass`, `fail` or
`inconclusive`. Missing evidence is inconclusive. Crash, timeout, external kill,
resource-budget breach, or any observed security violation fails. Behavior is
`pass`, `fail`, `unsupported`, `inconclusive` or `policy-dependent`. `accept` and
`recover` recipes require independently verified output; `reject` requires an
explicit rejection and an empty final output directory; `contain` permits either acceptance policy and cannot be
used to advertise compatibility. A client that rejects all controls cannot earn
a behavior pass. Neither a successful repair nor matching CRC authenticates an
attacker's content.

The immutable plan declares every case/client/repetition and automatically adds
required controls. Recorded results embed observations and freeze output verdicts;
comparison does not reopen directories that may have been cleaned up. Missing,
duplicate and unplanned attempts cannot quietly disappear from the denominator.
Strict evaluation, recording and planned comparison are the default: exit 1 for
known failures, exit 2 for incomplete or unsupported evidence. Legacy `compare`
requires `--strict=false` and is exploratory, not a comparison gate. JSON readers
reject duplicate keys, unknown fields, trailing data and excessive size/depth.

Keep any confirmed exploit evidence and reproducer private and notify the
maintainer before publishing a comparison, regression fixture or advisory. The
commands never create issues, send reports, publish results or contact a real
Usenet service.

## Verification

```sh
go test -race ./internal/adversarial ./cmd/adversarial
ADVERSARIAL_ORACLES=1 go test ./internal/adversarial \
  -run 'TestInstalledIndependentOracles|TestIndependentMultiSlicePAR2Oracle' -v
go test ./...
go vet ./...
```

The normal tests regenerate every case, verify deterministic manifests and
bounded artifacts, export and verify bundles, detect tampering/overwrite/link
attempts, check header hashes, decode positive controls, prove compressed bombs
cross the declared output limit, exercise NNTP framing/retry/cancellation, and
test scoring at every resource boundary. The optional oracle test requires
already-installed `7zz` and `par2`; it independently extracts valid RAR4/RAR5/7z
controls and verifies five successful repair cases against the source digest.
The multi-file oracle also checks bounded insufficient/dependent recovery cases;
a timeout or crash does not count as the expected rejection. Record tool versions when
using the results as generation evidence. No dependency installation occurs.
